# Feature Specification: Sites & Buildings Management

**Feature Branch**: `004-sites-buildings-management`

**Created**: 2026-11-27

**Status**: Draft

**Input**: User description: "GridAware — Phase 5.4: Sites & Buildings Management — first physical-location layer introducing organization-owned Sites and site-owned Buildings with strict multi-tenant isolation, normalized immutable codes, validated geographic/time-zone/physical metadata, operational status vs non-destructive archival lifecycle with dependency protection, role-based permission enforcement, structured mutation auditing, and role-aware accessible Sites & Buildings management screens."

## Clarifications

### Session 2026-11-27

- Q: Should Phase 5.4 deliver backend capabilities and contracts only, or also include frontend Sites & Buildings management screens in this sprint? (`FR-001`) → A: Option B — Deliver both the complete backend Sites & Buildings domain/contracts and the full set of role-aware, EVARAX-compliant, WCAG 2.2 AA Sites & Buildings management screens (sites list, create/edit site, site overview/details, buildings list within a site, create/edit building, building overview/details, status controls, and archive/restore confirmation dialogs), matching the full vertical-slice delivery pattern of prior phases.
- Q: Should creating or restoring a building be allowed under an `INACTIVE` (non-archived) parent site, or must the parent site be strictly `ACTIVE`? (`FR-010`) → A: Option A — Strictly require the parent site to be both non-archived and `ACTIVE` when creating a new building or restoring an archived building; attempting either against an `INACTIVE` or archived parent site fails with a conflict error so administrators explicitly activate the facility before expanding or restoring its buildings.
- Q: Who should be authorized to view archived sites and buildings when explicitly requesting archived records? (`FR-015`) → A: Option A — Restrict archived list filtering (`includeArchived`) and archived record detail access strictly to users holding the corresponding archive permission (`sites:archive` or `buildings:archive`, i.e., `Owner` and `Facility Manager`); active members with read-only roles (`Engineer`, `Technician`, `Viewer`) requesting archived views are denied as forbidden.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Manage Organization Sites (Priority: P1)

An authorized organization administrator (`Owner` or `Facility Manager`) creates, browses, searches, filters, inspects, and updates **Sites** (such as manufacturing plants, industrial facilities, commercial complexes, campuses, or warehouse parks) belonging to their active organization. Each site carries a normalized, immutable, organization-unique code, a human-readable name, a controlled site type, an operational time zone, and optional address and geographic coordinate metadata. All active members with site read access (`Owner`, `Facility Manager`, `Engineer`, `Technician`, `Viewer`) can list and inspect non-archived sites in their active organization—including a safe count of non-archived buildings within each site—while non-administrative roles cannot create or modify sites.

**Why this priority**: Sites establish the top-level physical location boundary beneath an organization; without sites, buildings cannot be organized and future assets, sensors, telemetry, incidents, and maintenance records have no physical hierarchy.

**Independent Test**: Can be fully tested by signing in as an `Owner` or `Facility Manager`, creating multiple sites with valid codes, names, types, addresses, coordinates, and time zones, listing sites with search, status filter, sorting, and pagination, inspecting individual site details and building counts, updating editable metadata, verifying duplicate code and invalid input rejection, and confirming `Engineer`/`Technician`/`Viewer` can read but not create or edit sites.

**Acceptance Scenarios**:

1. **Given** an authenticated `Owner` or `Facility Manager` acting in an active organization, **When** they create a site with a valid code (e.g., `cai-plant-01`), name, controlled site type, optional address/coordinates, and valid time zone, **Then** the code is normalized to uppercase (`CAI-PLANT-01`), the site is created as `ACTIVE` under the verified active organization (ignoring any client-supplied ownership fields), and the created site details are returned.
2. **Given** an organization that already has a site with code `CAI-PLANT-01`, **When** an authorized user attempts to create another site with code `cai-plant-01` or `CAI-PLANT-01` in the same organization, **Then** the system rejects the request with a duplicate-code conflict error and persists no new record; **When** a different organization creates a site with code `CAI-PLANT-01`, **Then** it succeeds because site codes are scoped per organization.
3. **Given** an active organization with multiple active, inactive, and archived sites, **When** an authorized member lists sites with default filters, **Then** only non-archived sites belonging to their active organization are returned in deterministic order with pagination support and safe building counts, and searching by code/name or filtering by status narrows results strictly within that organization.
4. **Given** an existing non-archived site, **When** a `Facility Manager` updates editable fields (such as name, description, address, coordinate pair, or time zone), **Then** the changes are persisted and returned; **When** they attempt to alter immutable fields (identifier, owning organization, site code, archive timestamp, or creation metadata) or submit an empty update, **Then** the request is rejected.
5. **Given** an authenticated `Engineer`, `Technician`, or `Viewer` in an active organization, **When** they list or view site details, **Then** access is granted; **When** they attempt to create or update a site, **Then** access is denied as forbidden and no data is changed.

### User Story 2 - Manage Buildings Within Sites (Priority: P1)

An authorized organization administrator (`Owner` or `Facility Manager`) creates, lists, searches, filters, inspects, and updates **Buildings** (such as production halls, office towers, warehouses, utility buildings, retail buildings, plant rooms, or parking structures) nested strictly inside a specific active site belonging to their active organization. Each building has a normalized, immutable, site-unique code, a human-readable name, a controlled building type, and optional description, floor count, and gross area in square meters. Standalone single-building properties are represented consistently as one site containing one building. All active organization members with building read access can list and inspect non-archived buildings within an accessible site, while cross-site and cross-tenant building access is strictly blocked.

**Why this priority**: Buildings complete the Phase 5.4 physical hierarchy (`Organization -> Site -> Building`) needed by downstream asset, sensor, and maintenance workflows, and enforcing strict parent-site and tenant coupling from day one prevents orphaned or cross-tenant records.

**Independent Test**: Can be fully tested by creating an active site under an organization, adding multiple buildings (e.g., `Production Hall 1`, `Utilities Building`, `Warehouse`) under that site, verifying the parent site's building count updates accurately, listing and filtering buildings within the site, updating editable building fields, attempting duplicate building codes within the same site vs another site, and verifying that requesting a building under the wrong site or organization fails without disclosing the building's existence.

**Acceptance Scenarios**:

1. **Given** an active, non-archived site in the user's active organization and an authorized `Owner` or `Facility Manager`, **When** they create a building under that site with a valid code, name, controlled building type, optional floor count, and optional gross floor area, **Then** the building is persisted with both the verified organization and parent site, initialized as `ACTIVE`, and reflected in the parent site's building count.
2. **Given** a site that already contains a building with code `PROD-HALL-01`, **When** an authorized user attempts to create another building with code `prod-hall-01` under the same site, **Then** the system rejects the request with a duplicate-code conflict error; **When** they create a building with code `PROD-HALL-01` under a different active site in the same organization, **Then** it succeeds because building codes are unique per site.
3. **Given** a site containing multiple buildings and a second site containing other buildings in the same organization, **When** a member lists buildings under Site 1, **Then** only non-archived buildings belonging to Site 1 are returned; **When** a member requests a building belonging to Site 2 through Site 1's path even with its exact identifier, **Then** the system returns a non-disclosing not-found error.
4. **Given** an existing non-archived building, **When** an authorized user updates editable fields (name, type, description, floor count, gross area), **Then** the changes are saved; **When** they attempt to change the building's code, parent site, or owning organization through update, **Then** the request is rejected.
5. **Given** an archived or `INACTIVE` parent site, **When** an authorized user attempts to create a new building under that site, **Then** the system rejects the creation with a conflict error explaining the parent site state.

### User Story 3 - Control Operational Status and Non-Destructive Archival Lifecycle (Priority: P1)

Authorized administrators (`Owner` or `Facility Manager`) manage the lifecycle of sites and buildings without destructive deletion. Operational status (`ACTIVE` vs `INACTIVE`) is managed independently of archival state: administrators can deactivate an unused site or building while retaining its history, and reactivate it later. When a location is retired, administrators with archive permission can archive it non-destructively so it disappears from standard lists while preserving audit history and code reservation. Archiving a site is blocked whenever the site still has any non-archived buildings (requiring administrators to archive buildings first rather than silently cascading). Administrators with archive permission can inspect archived sites and buildings via explicit archive views and restore them when parent validity (`ACTIVE`, non-archived parent site for buildings) and uniqueness preconditions hold.

**Why this priority**: Industrial and commercial facility platforms must preserve historical location identity for auditability and future asset/telemetry lineage; separating operational status from non-destructive archival and blocking unsafe parent archival prevents accidental data loss and broken references.

**Independent Test**: Can be fully tested by deactivating and reactivating both a site and a building (verifying site deactivation does not archive or alter child buildings), attempting to archive a site that still has non-archived buildings (verifying conflict rejection), archiving all child buildings and then archiving the site (verifying success and exclusion from default lists), querying archived locations as an administrator vs a non-administrator, attempting to restore a child building while its parent site is archived or inactive (verifying conflict rejection), and then restoring and activating the site followed by restoring the building.

**Acceptance Scenarios**:

1. **Given** an active site containing active buildings, **When** an authorized administrator deactivates the site, **Then** the site's status becomes `INACTIVE`, its buildings are not automatically archived or deleted, and the administrator can later reactivate the site back to `ACTIVE`.
2. **Given** a site that contains at least one non-archived building (whether `ACTIVE` or `INACTIVE`), **When** an authorized administrator attempts to archive the site, **Then** the system rejects the request with a conflict error explaining that non-archived buildings exist and does not cascade-archive any child buildings.
3. **Given** a site whose buildings have all been archived (or a site with no buildings), **When** an authorized administrator archives the site, **Then** the site receives an archive timestamp, is excluded from default site listings, remains viewable via authorized archive views, and retains its reserved code so future sites in the organization cannot reuse it.
4. **Given** an archived building whose parent site is archived or `INACTIVE`, **When** an authorized administrator attempts to restore the building, **Then** the system rejects the restore with a conflict error; **When** the parent site is non-archived and `ACTIVE` and the administrator restores the building, **Then** the restoration succeeds and the building returns to normal listings with its archive timestamp cleared.
5. **Given** an `Engineer`, `Technician`, or `Viewer`, **When** they attempt to activate, deactivate, archive, restore, or explicitly view archived sites or buildings, **Then** the system denies the action as forbidden.

### User Story 4 - Enforce Multi-Tenant Isolation, Role Permissions, and Mutation Auditability (Priority: P1)

Every location operation enforces strict tenant isolation and role-based access control derived exclusively from server-verified active organization membership, never trusting client-supplied ownership identifiers. A member of Organization A—even an `Owner`—cannot list, inspect, create, update, deactivate, archive, or restore any site or building belonging to Organization B, nor attach a building in Organization A to a site in Organization B. Every successful creation, update, activation, deactivation, archive, and restore produces a tamper-resistant, tenant-scoped audit record capturing actor, organization, target location, timestamp, correlation identifier, and safe change metadata within the same transactional boundary so failed mutations never emit misleading audit entries.

**Why this priority**: Tenant isolation and complete audit trails are non-negotiable platform governance requirements (Constitution Principles I and VII); any cross-tenant leak or unaudited administrative change breaks enterprise trust and compliance.

**Independent Test**: Can be fully tested with two independent organizations (Organization A and Organization B) and users across all five roles plus a non-member, verifying that cross-tenant reads/writes/pagination cursors and cross-tenant parent references are rejected without revealing foreign resource existence, suspended memberships or inactive organizations fail closed, and every successful mutation generates an atomic audit event containing accurate metadata and zero secrets.

**Acceptance Scenarios**:

1. **Given** an `Owner` of Organization A who knows the exact identifier of a site or building in Organization B, **When** they attempt to view, update, deactivate, archive, restore, or add a building to Organization B's location, **Then** the platform rejects the request with a non-disclosing error so Organization B's resource existence is never confirmed.
2. **Given** an authenticated user with a pagination cursor obtained from Organization B (or an unjoined organization), **When** they supply that cursor while listing Organization A's locations, **Then** the system rejects the foreign cursor without disclosing any Organization B records.
3. **Given** a user whose membership is suspended or whose organization is inactive/archived, **When** they attempt any site or building read or write action, **Then** the platform fails closed and denies access.
4. **Given** an authorized user performing any site or building mutation (create, update, activate, deactivate, archive, or restore), **When** the mutation succeeds, **Then** an audit event of the corresponding type (`SITE_CREATED`, `SITE_UPDATED`, `SITE_ACTIVATED`, `SITE_DEACTIVATED`, `SITE_ARCHIVED`, `SITE_RESTORED`, `BUILDING_CREATED`, `BUILDING_UPDATED`, `BUILDING_ACTIVATED`, `BUILDING_DEACTIVATED`, `BUILDING_ARCHIVED`, `BUILDING_RESTORED`) is recorded atomically with organization, actor, target type and identifier, timestamp, correlation identifier, and safe change metadata; **When** the mutation fails (e.g., validation error or conflict), **Then** no audit event for that mutation is persisted.

### User Story 5 - Deliver Role-Aware, Accessible Sites & Buildings Management Screens (Priority: P2)

Authenticated organization members manage and inspect their organization's physical locations through dedicated, dark-first EVARAX-styled, keyboard-accessible Sites & Buildings screens integrated into the active organization workspace. Users can browse, search, filter, and paginate sites; open a site's overview to view its location metadata, operational time zone, and nested buildings list; inspect individual building details; and—when their server-computed organization capabilities allow—create sites, edit site metadata, add and edit buildings, toggle operational status, filter archived locations, and archive or restore sites and buildings through clear confirmation dialogs. When archiving a site is blocked by existing buildings, the interface clearly explains the dependency and links directly to that site's buildings list.

**Why this priority**: Delivering the end-to-end management screens alongside the domain capabilities lets `Owner` and `Facility Manager` users configure real facility hierarchies immediately while giving `Engineer`, `Technician`, and `Viewer` personas clean read-only location views that follow Constitution Principle VIII.

**Independent Test**: Can be fully tested by signing in as an `Owner`, `Facility Manager`, and `Viewer` across desktop and mobile viewports: verifying full site creation, editing, building creation/editing, deactivation, archive-blocked guidance, archive, and restore flows for administrators; confirming `Viewer` sees read-only views with no create/edit/archive/archived-filter controls; testing keyboard-only navigation, non-color-only status indicators, loading/empty/error/permission-denied states; and switching organizations to confirm previous-tenant location state is immediately cleared.

**Acceptance Scenarios**:

1. **Given** an `Owner` or `Facility Manager` opening the Sites section of their active organization, **When** the organization has no sites yet, **Then** an accessible empty state guides them to create their first site; **When** they create a site and add buildings, **Then** site names appear as primary titles with codes presented as technical identifiers, operational status badges pair color with text/icon labels (never claiming equipment health), and site timestamps respect the site's configured time zone where local time is shown.
2. **Given** an administrator attempting to archive a site that still contains non-archived buildings via the archive confirmation dialog, **When** the backend rejects the request because active/non-archived buildings remain, **Then** the UI explains the building dependency clearly and provides a direct action/link to open the site's buildings list so the user can archive buildings first.
3. **Given** a `Viewer`, `Engineer`, or `Technician` viewing the Sites or Site Details screens, **When** the page loads using server-computed capability context, **Then** create, edit, activate/deactivate, archive, restore, and archived-records filter controls are hidden or unavailable, while all permitted location details remain clearly readable.
4. **Given** a multi-organization user viewing Site A in Organization 1, **When** they switch to Organization 2, **Then** Organization 1's sites and buildings state is immediately cleared, Organization 2's sites and capabilities are loaded, and attempting to navigate directly to a foreign organization's or site's URL renders an accessible not-found or permission-denied state without leaking foreign existence.
5. **Given** any user navigating the Sites & Buildings screens via keyboard or assistive technology, **When** interacting with search/filter controls, lists, forms, validation errors, and archive/restore confirmation dialogs, **Then** focus order, visible focus indicators, form error associations, contrast, and reduced-motion preferences meet WCAG 2.2 Level AA standards.

### Edge Cases

- **Partial geographic coordinates**: Submitting latitude without longitude, or longitude without latitude, or non-finite/out-of-range coordinates (outside `-90..90` for latitude or `-180..180` for longitude) MUST be rejected with a validation error. Both coordinates must be provided together or omitted/cleared together.
- **Invalid code formats and whitespace**: Codes with leading/trailing spaces are trimmed and converted to uppercase before validation, but internal spaces MUST NOT be silently converted to hyphens; codes shorter than 2 or longer than 32 characters, containing characters outside `A-Z`, `0-9`, and `-`, or having leading, trailing, or consecutive hyphens (`--`) MUST be rejected.
- **Concurrent duplicate code creation**: Two simultaneous requests creating sites with the same normalized code in the same organization (or buildings with the same normalized code in the same site) MUST allow at most one to succeed and deterministically return a duplicate-code conflict for the other.
- **Concurrent site archive and building creation**: If a building is created under a site concurrently while an administrator attempts to archive that site, transactional checks MUST prevent ending up with an archived site containing a non-archived building.
- **Mutations on archived locations**: Attempting to update metadata, activate, deactivate, or re-archive an already-archived site or building MUST be rejected with an invalid-state conflict until the record is explicitly restored; attempting to restore a location that is not archived MUST also fail with an invalid-state conflict.
- **Redundant status transitions**: Attempting to activate an already-active location or deactivate an already-inactive location MUST fail deterministically with an invalid-state conflict rather than silently emitting spurious audit events.
- **Building creation or restoration under an `INACTIVE` parent site**: Even if the parent site is not archived, if its operational status is `INACTIVE`, creating a new building under it or restoring an archived building under it MUST fail with a conflict error until the parent site is activated.
- **Building lookup under wrong site in same organization**: Requesting Building X (belonging to Site B) via Site A's path within the same organization MUST return a non-disclosing building-not-found error.
- **Unauthorized archive viewing**: An active `Engineer`, `Technician`, or `Viewer` requesting `includeArchived=true` or directly requesting an archived site or building MUST be denied as forbidden rather than receiving archived records or silently stripping the filter.
- **Hard-delete prohibition**: No generic hard-delete action is exposed for sites or buildings; organizations, sites, and buildings with child records are protected against destructive deletion.
- **Unicode names and control characters**: Site and building names MUST trim leading/trailing whitespace, preserve user capitalization, support Unicode characters (e.g., Arabic, accented Latin), enforce length between 2 and 120 characters, and reject empty strings or control characters.
- **Time-zone validation**: Submitting a fixed numeric offset (such as `+02:00`) or an unrecognized string as a site time zone MUST be rejected; only recognized IANA time-zone identifiers (such as `Africa/Cairo`, `Europe/London`, or `UTC`) are accepted.
- **Physical measurement bounds**: `floorCount` must be a positive integer when provided (rejecting `0`, negative numbers, decimals, or unrealistic values above the configured upper bound); `grossAreaSqM` must be strictly greater than zero with at most two decimal places when provided.
- **Location status vs equipment health**: An `ACTIVE` site or building status indicates only that the location record is enabled for operational use and MUST NOT be interpreted or presented as indicating that assets or equipment at that location are healthy.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (Scope & Delivery Boundary)**: System MUST deliver both the complete organization-scoped Sites & Buildings backend domain (persistence invariants, validation, authorization, lifecycle, auditability, and stable frontend contracts) and the full set of role-aware, EVARAX-compliant, WCAG 2.2 AA Sites & Buildings management screens within the active organization workspace.
- **FR-002 (List Sites)**: System MUST allow authenticated active members with `sites:read` permission to list non-archived sites belonging strictly to their active organization, supporting cursor pagination (default 20, maximum 100), text search across `code` and `name`, filtering by operational `status` (`ACTIVE` or `INACTIVE`), and deterministic allow-listed ordering (`createdAt`, `name`, or `code`, ascending or descending, defaulting to newest first with deterministic tie-breaking), returning a safe count of non-archived child buildings per site.
- **FR-003 (Create Site)**: System MUST allow authenticated active members with `sites:create` permission to create a site under their verified active organization with a normalized uppercase unique `code`, trimmed `name`, controlled `SiteType`, valid IANA `timeZone` (defaulting to `UTC`), optional `description`, optional address fields (`addressLine1`, `addressLine2`, `city`, `region`, `postalCode`, uppercase ISO 3166-1 alpha-2 `countryCode`), and optional `latitude`/`longitude` pair, rejecting client-supplied ownership/system fields and mapping concurrent duplicate codes to a conflict error.
- **FR-004 (Read Site Details)**: System MUST allow authenticated active members with `sites:read` permission to retrieve full details (including safe building count) of a single non-archived site belonging to their active organization, returning a non-disclosing not-found error when the site does not exist or belongs to another organization.
- **FR-005 (Update Site)**: System MUST allow authenticated active members with `sites:update` permission to update allow-listed editable metadata on a non-archived site within their active organization, rejecting empty updates, unknown fields, and attempts to modify immutable fields (`id`, `organizationId`, `code`, `archivedAt`, `createdAt`, `updatedAt`, creator identity).
- **FR-006 (Site Operational Status)**: System MUST allow authenticated active members with `sites:update` permission to explicitly activate (`ACTIVE`) or deactivate (`INACTIVE`) a non-archived site without deleting data or automatically modifying or archiving child buildings.
- **FR-007 (Archive Site)**: System MUST allow authenticated active members with `sites:archive` permission to archive a non-archived site non-destructively by recording an archive UTC timestamp, and MUST reject the archival with a conflict error whenever the site still contains any non-archived building (never cascading archival silently).
- **FR-008 (List Buildings)**: System MUST allow authenticated active members with `buildings:read` permission to list non-archived buildings scoped strictly to a verified parent site within their active organization, supporting the same bounded cursor pagination, search (`code`, `name`), status filtering, and allow-listed deterministic sorting rules as sites; no unscoped global buildings list is exposed.
- **FR-009 (Create Building)**: System MUST allow authenticated active members with `buildings:create` permission to create a building under a verified parent site in their active organization with a site-unique normalized uppercase `code`, trimmed `name`, controlled `BuildingType`, optional `description`, optional positive integer `floorCount`, and optional positive decimal `grossAreaSqM` (up to 2 decimal places), deriving both owning organization and parent site strictly from verified context rather than request body input.
- **FR-010 (Parent Site Lifecycle Policy for Building Creation & Restore)**: System MUST require the parent site to be both non-archived and `ACTIVE` whenever creating a new building or restoring an archived building; attempting either operation while the parent site is archived or `INACTIVE` MUST fail with a conflict error and stable domain error code.
- **FR-011 (Read Building Details)**: System MUST allow authenticated active members with `buildings:read` permission to retrieve a building only when the building identifier, parent site identifier, and active organization identifier all match a non-archived record (or an archived record under FR-015), returning a non-disclosing not-found error otherwise.
- **FR-012 (Update Building)**: System MUST allow authenticated active members with `buildings:update` permission to update allow-listed editable metadata on a non-archived building within its verified site and organization, disallowing code changes and moving buildings between sites or organizations.
- **FR-013 (Building Operational Status & Archive)**: System MUST allow authenticated active members with `buildings:update` permission to activate or deactivate a non-archived building, and members with `buildings:archive` permission to archive a non-archived building non-destructively without exposing any hard-delete operation.
- **FR-014 (Restore Archived Locations)**: System MUST allow authenticated active members with `sites:archive` or `buildings:archive` permission to restore an archived site or building by clearing its archive timestamp, provided the owning organization is active, parent-site validity rules (FR-010) are satisfied, and code uniqueness remains intact.
- **FR-015 (Archived Location Visibility Policy)**: System MUST exclude archived sites and buildings from default list and detail views; explicitly requesting archived records (`includeArchived` filter or archived detail view) MUST require the corresponding archive permission (`sites:archive` for sites, `buildings:archive` for buildings, held by `Owner` and `Facility Manager`), denying unauthorized members with a forbidden error.
- **FR-016 (Strict Data Validation & Code Immutability)**: System MUST validate all site and building inputs at runtime, rejecting unknown properties, invalid enum values, invalid code syntax (2–32 characters, uppercase ASCII letters/digits and single internal hyphens only, no silent space rewriting), invalid names (2–120 trimmed characters, no control characters), invalid IANA time zones, mismatched or out-of-range latitude/longitude pairs, invalid ISO alpha-2 country codes, and invalid floor counts or areas; codes MUST remain immutable and non-reusable after archival.
- **FR-017 (Multi-Tenant & Role-Based Security Enforcement)**: System MUST enforce authentication, active organization context, active membership, and Phase 5.3 permissions (`sites:read`, `sites:create`, `sites:update`, `sites:archive`, `buildings:read`, `buildings:create`, `buildings:update`, `buildings:archive`) server-side on every operation, enforce same-tenant parent-child integrity at both service and persistence layers, fail closed on missing/suspended context or unknown permissions, validate pagination cursors against the active tenant and scope, and conceal cross-tenant resource existence.
- **FR-018 (Transactional Auditability & Observability)**: System MUST record an immutable, tenant-scoped audit event (`SITE_CREATED`, `SITE_UPDATED`, `SITE_ACTIVATED`, `SITE_DEACTIVATED`, `SITE_ARCHIVED`, `SITE_RESTORED`, `BUILDING_CREATED`, `BUILDING_UPDATED`, `BUILDING_ACTIVATED`, `BUILDING_DEACTIVATED`, `BUILDING_ARCHIVED`, `BUILDING_RESTORED`) atomically with every successful location mutation—capturing organization, actor, target type and ID, UTC timestamp, correlation ID, and safe change metadata without secrets—and emit structured operational logs and low-cardinality mutation/conflict metrics.
- **FR-019 (Role-Aware, Accessible Management Interface)**: System MUST provide EVARAX-compliant, WCAG 2.2 Level AA screens for sites list, create/edit site, site overview/details, buildings list within a site, create/edit building, building overview/details, status controls, and archive/restore confirmation dialogs—rendering mutation and archive-view controls strictly from server-computed capability context, displaying names as titles and codes as technical identifiers, distinguishing operational location status from equipment health with non-color-only badges, explaining building dependencies with a direct navigation link when site archival is blocked, implementing explicit loading/empty/error/permission-denied states, and clearing previous-tenant view state on organization switch.

### Key Entities *(include if feature involves data)*

- **Organization** *(existing tenant boundary)*: Owns zero or more Sites and Buildings; every Site and Building belongs to exactly one Organization.
- **Site**: A logical facility, campus, plant, or operational property belonging to an Organization. Key attributes: immutable identifier, owning organization reference, normalized unique-per-organization immutable `code`, human-readable `name`, controlled `SiteType` (`FACTORY`, `INDUSTRIAL_FACILITY`, `COMMERCIAL_COMPLEX`, `COMMERCIAL_PROPERTY`, `CAMPUS`, `WAREHOUSE_CAMPUS`, `OTHER`), optional description, optional postal address fields (`addressLine1`, `addressLine2`, `city`, `region`, `postalCode`, `countryCode`), optional paired `latitude` and `longitude`, IANA `timeZone` (default `UTC`), operational `status` (`ACTIVE` or `INACTIVE`), optional `archivedAt` UTC timestamp, and creation/update timestamps. Contains zero or more Buildings.
- **Building**: A physical building situated within exactly one Site and owned by the same Organization as that Site. Key attributes: immutable identifier, owning organization reference, parent site reference (enforced to share the same organization), normalized unique-per-site immutable `code`, human-readable `name`, controlled `BuildingType` (`PRODUCTION`, `OFFICE`, `WAREHOUSE`, `UTILITY`, `RETAIL`, `PLANT_ROOM`, `PARKING`, `OTHER`), optional description, optional positive integer `floorCount`, optional positive decimal `grossAreaSqM` (up to two decimal places), operational `status` (`ACTIVE` or `INACTIVE`), optional `archivedAt` UTC timestamp, and creation/update timestamps.
- **Location Audit Event**: An immutable, tenant-scoped record written atomically with every site or building mutation, capturing the owning organization, acting user, event type, target resource type (`SITE` or `BUILDING`), target resource identifier, UTC timestamp, request correlation identifier, and safe before/after change summary.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An authorized `Owner` or `Facility Manager` can set up a complete facility hierarchy (create a site and add three buildings under it, then inspect the site with an accurate building count of 3) in under 2 minutes with 100% validation accuracy on first submission of valid data.
- **SC-002**: 100% of cross-tenant access attempts (across reads, listings, updates, status changes, archives, restores, pagination cursors, and cross-tenant building-to-site attachments) and cross-site building lookups are blocked with zero leakage of foreign tenant data or resource existence.
- **SC-003**: 100% of role permission rules across all five roles (`Owner`, `Facility Manager`, `Engineer`, `Technician`, `Viewer`) and non-members/suspended memberships are enforced consistently on every site, building, and archived-view operation, with zero unauthorized records created or modified.
- **SC-004**: 100% of concurrent duplicate-code submissions and concurrent site-archive vs building-creation operations preserve uniqueness and parent-child archival invariants with zero orphaned buildings or duplicate codes within scope.
- **SC-005**: 100% of successful site and building mutations produce a matching, complete, secret-free audit record, and 0% of failed or rejected requests produce spurious audit records.
- **SC-006**: Ordinary authenticated site and building list and detail lookups complete within the platform's interactive responsiveness target (`p95` under 300 ms, ceiling under 500 ms) under bounded pagination without loading unbounded child collections.
- **SC-007**: Zero hard-delete paths exist for sites or buildings, and 100% of archived locations remain recoverable through authorized restoration once parent preconditions are satisfied while preserving code immutability.
- **SC-008**: 100% of primary Sites & Buildings management journeys (list, create, view, edit, activate/deactivate, archive-blocked guidance, archive, restore, and organization switching) are completable using keyboard-only navigation, pass WCAG 2.2 Level AA contrast and non-color status cue checks, and display accurate capability-gated controls for all five roles.

## Assumptions

- **Prerequisite phases**: Authentication (Phase 5.1), Organizations & Memberships (Phase 5.2), Role-Based Access Control & Permissions catalogue (`sites:*`, `buildings:*`) (Phase 5.3), and core error/response/logging/audit/frontend capability foundations are already implemented in the repository and will be reused directly without duplication.
- **Explicit non-goals for this phase**: Assets and equipment hierarchy (Phase 5.5), sensors/devices, telemetry ingestion, AI predictions/anomalies, work orders and maintenance records, floor/room/zone sub-hierarchies, CAD/BIM/floor-plan uploads, maps/geofencing/spatial queries, custom user-defined fields, bulk import/export, and billing/subscriptions are out of scope.
- **Numeric & text bounds defaults**: `description` is bounded to 2,000 characters; address fields (`addressLine1`, `addressLine2`, `city`, `region`) are bounded to 200 characters (postal code to 32 characters); `floorCount` when supplied is bounded between 1 and 200; `grossAreaSqM` when supplied is strictly greater than `0` and up to `9,999,999,999.99` (two decimal places).
- **Building count semantics**: The `buildingCount` reported on site list and detail responses counts non-archived buildings under that site so administrators immediately know how many active/inactive buildings exist (and whether archival is currently blocked).
- **Development/demo fixtures**: Sample demo organizations, sites (`Cairo Manufacturing Plant`, `Cairo Business Park`), and buildings (`Production Hall 1`, `Utilities Building`, `Warehouse`, `Tower A`, `Tower B`) are strictly labeled as development/demo seed data and are never automatically seeded into production environments.
- **Future asset-phase extensibility**: The building and site archive workflows and composite tenant-safe identifiers are structured so Phase 5.5 (Assets & Equipment) can cleanly attach assets (site-level or building-level) and add active-asset archival preconditions without redesigning Phase 5.4.
