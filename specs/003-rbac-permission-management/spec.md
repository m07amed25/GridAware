# Feature Specification: Role-Based Access Control & Permission Management

**Feature Branch**: `003-rbac-permission-management`

**Created**: 2026-11-27

**Status**: Draft

**Input**: User description: "GridAware — Phase 5.3: Role-Based Access Control & Permission Management — organization-scoped authorization layer for the five fixed roles (Owner, Facility Manager, Engineer, Technician, Viewer), central permission catalogue and role-to-permission mapping, deny-by-default request and resource-level enforcement, technician work-order assignment scoping, safe member role administration with last-owner protection, frontend capability context, cross-channel enforcement (real-time subscriptions, background jobs, exports, device separation), and security auditing."

## Clarifications

### Session 2026-11-27

- Q: Which operational permission baseline should govern `Engineer` and `Facility Manager` for infrastructure and work-order completion? (`FR-003`) → A: Option B — Align with the PRD and User Stories (`US-006`, `US-008`, `US-014`): allow `Engineer` to create and update assets, configure sensors, and manage thresholds (keeping site/building management and all resource archiving restricted to `Owner` and `Facility Manager`), and grant tenant-wide `work-orders:update` and `work-orders:complete` to `Owner`, `Facility Manager`, and `Engineer`.
- Q: What consistent error behavior should apply when an authenticated user requests an unjoined, non-existent, or inactive organization, or holds an inactive/removed membership? (`FR-008`) → A: Option A — Strict concealment: uniformly return a non-disclosing "Not Found" response for unjoined, non-existent, or inactive organizations, inactive/removed memberships, and cross-tenant child resource lookups; return "Forbidden" only when an active member of an active organization lacks a required permission.
- Q: How should `Technician` access be scoped for non-work-order operational records (`Assets`, `Sensors`, `Telemetry`, `Anomalies`, `Predictions/Risk`, `Incidents`, `Maintenance History`)? (`FR-012`) → A: Option A — Strictly assignment-related scope: `Technician` members can read basic organization/site/building context plus their own notifications, while operational reads on assets, sensors, telemetry, anomalies, summary risk/predictions, maintenance history, and linked incidents (including adding notes on linked incidents) are strictly restricted to records linked to work orders assigned to that `Technician`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Enforce Organization Context and Role-Based Permissions on Every Request (Priority: P1)

Every authenticated user interacting with an organization-scoped capability is authorized on every request against a server-verified active membership in an active organization. A user who belongs to multiple organizations with different roles—for example, `Owner` in Organization A and `Viewer` in Organization B—receives only the permissions granted by their role in the specific organization they are acting within, and any role downgrade, suspension, or removal takes effect immediately on subsequent requests without requiring the user to sign out. Any protected operation that lacks an explicit permission rule, an active organization context, or a recognized role fails closed.

**Why this priority**: Organization-scoped, deny-by-default authorization is the foundational security boundary for a multi-tenant B2B platform; without verified membership context and strict role enforcement on every operation, no downstream operational capability can safely expose tenant data.

**Independent Test**: Can be tested end-to-end by assigning the same authenticated user different roles in two active organizations, exercising permitted and forbidden actions across all five roles (`Owner`, `Facility Manager`, `Engineer`, `Technician`, `Viewer`), modifying a member's role or suspending their membership mid-session to verify immediate enforcement on the next request, and attempting requests with missing authentication, inactive organizations, or undeclared permission policies to confirm fail-closed denial.

**Acceptance Scenarios**:

1. **Given** an unauthenticated caller attempting any protected organization-scoped action, **When** the request is received, **Then** the platform denies access as unauthenticated before evaluating organization membership or permissions.
2. **Given** an authenticated user who holds `Owner` in Organization A and `Viewer` in Organization B, **When** they attempt an administrative write action in Organization A, **Then** the action succeeds; **When** they attempt the same write action in Organization B, **Then** the platform rejects it as forbidden.
3. **Given** an authenticated user whose membership role is downgraded from `Facility Manager` to `Viewer` (or whose membership is suspended) while they hold an active session, **When** they issue their very next write request without signing out, **Then** the platform immediately denies the request based on their current server-side membership state rather than stale session claims.
4. **Given** an authenticated user who supplies a forged organization identifier, role name, or membership identifier in request input, **When** the platform evaluates authorization, **Then** the forged fields are ignored as authority and access is determined strictly from the authenticated user's active membership in the target organization.
5. **Given** a protected operation that has no declared permission requirement, or a membership bearing an unrecognized role value, **When** any user attempts to invoke it, **Then** the platform fails closed and denies access.

### User Story 2 - Enforce Tenant-Scoped Resource Access and Technician Assignment Boundaries (Priority: P1)

Permission checks do not stop at coarse role capabilities: every read, list, create, update, and state transition verifies that the targeted record and all referenced parent or related records belong to the active organization. For `Technician` members, work-order access and execution are further constrained at the record and list-query level to work orders assigned to that technician, and state transitions re-verify both assignment and valid workflow state atomically at write time.

**Why this priority**: Coarse role permissions alone cannot prevent cross-tenant identifier substitution or unauthorized field-technician access to unassigned work; record-level and query-level enforcement closes broken object-level authorization vulnerabilities across every operational domain.

**Independent Test**: Can be tested independently by creating operational records (sites, buildings, assets, sensors, incidents, work orders) in Organization A and Organization B plus work orders assigned to Technician 1 and Technician 2 within Organization A, then verifying that cross-tenant lookups/mutations are rejected without leaking resource existence, that Technician 1's list and detail views only include Technician 1's assigned work orders, and that Technician 1 cannot reassign work or submit completion after a work order is reassigned away.

**Acceptance Scenarios**:

1. **Given** an `Owner` of Organization A who knows the exact identifier of an asset, incident, or work order belonging to Organization B, **When** they attempt to read, update, or attach child records to that Organization B resource, **Then** the platform rejects the operation without confirming whether the foreign resource exists.
2. **Given** an active organization with work orders assigned to Technician 1, work orders assigned to Technician 2, and unassigned work orders, **When** Technician 1 lists work orders, **Then** the query returns only work orders assigned to Technician 1 (never filtering an unrestricted full-tenant result set in memory).
3. **Given** a work order assigned to Technician 1, **When** Technician 1 updates permitted execution fields (inspection findings, maintenance notes, parts used) and submits completion while the work order is in an eligible status, **Then** the update succeeds; **When** Technician 1 attempts to change the work order's assignee or owning organization, or attempts to view or update a work order assigned to Technician 2, **Then** the platform rejects the request.
4. **Given** a work order that is reassigned from Technician 1 to Technician 2 concurrently while Technician 1 attempts to submit completion, **When** Technician 1's completion request executes, **Then** the write-time authorization and state check rejects the stale mutation cleanly with a conflict or non-disclosure denial.
5. **Given** an authorized user creating a child record (such as an asset under a site/building or a work order linked to an asset/incident), **When** any referenced parent record belongs to a different organization, **Then** the platform rejects the operation so cross-tenant links can never be created.

### User Story 3 - Safely Administer Organization Member Roles and Protect Ownership Invariants (Priority: P1)

An organization `Owner` can review organization members, invite eligible new members with permitted non-owner roles, update a member's role among supported non-owner roles, suspend or reactivate eligible memberships, and remove memberships—while strict server-side invariants prevent self-escalation, block granting or revoking `Owner` via generic role updates, and guarantee that an active organization can never be left without at least one active `Owner`, even under concurrent administrative requests.

**Why this priority**: Membership and role administration controls who can access customer infrastructure data; flawed role-management rules directly enable privilege escalation or permanent lockouts of an organization workspace.

**Independent Test**: Can be tested by having an `Owner` list members, change a `Viewer` to `Engineer`, suspend and reactivate a member, and remove a member, while verifying that non-owners are denied member administration, that a user cannot escalate their own role, that generic role updates reject promoting to or demoting from `Owner`, and that two concurrent requests attempting to remove or suspend the last active `Owner`(s) always preserve at least one active `Owner`.

**Acceptance Scenarios**:

1. **Given** an organization `Owner` viewing the organization's membership roster, **When** they update an active member's role from `Viewer` to `Engineer`, **Then** the membership role is updated, an audit event recording the previous and new role is created atomically, and the affected member's next request reflects `Engineer` permissions.
2. **Given** a `Facility Manager`, `Engineer`, `Technician`, or `Viewer`, **When** they attempt to list organization members, invite users, change any member's role, suspend/reactivate, or remove a membership, **Then** the platform denies the action as forbidden.
3. **Given** any member (including an `Owner` or non-owner), **When** they attempt to escalate their own role or use the generic role-update action to assign or revoke the `Owner` role, **Then** the platform rejects the request and directs ownership changes exclusively through the dedicated ownership-transfer workflow.
4. **Given** an active organization with only one active `Owner`, **When** any request attempts to demote, suspend, or remove that final active `Owner` (or when two concurrent requests attempt to remove or suspend the last two active `Owner`s simultaneously), **Then** the platform rejects the operation that would leave zero active `Owner`s with a conflict error while preserving at least one active `Owner`.
5. **Given** an `Owner` issuing a membership invitation, **When** they specify `Owner` as the invited role, **Then** the platform rejects the invitation because ownership cannot be granted through standard member invitations.

### User Story 4 - Deliver Role-Aware Interface Capabilities Without Relying on Client Enforcement (Priority: P2)

When an authenticated user enters or switches into an active organization, the application retrieves that user's current server-computed role, effective permissions, and policy version so the user interface can tailor navigation, hide or disable unavailable actions, show read-only views for `Viewer` users, focus `Technician` workflows on assigned work, and hide organization administration from non-owners. Whenever the user switches organizations, refreshes their session, or experiences a role change, the interface refreshes capabilities and clears previous-tenant view state, while all security enforcement remains exclusively on the backend.

**Why this priority**: Role-aware presentation prevents operational confusion and accidental unauthorized action attempts across five distinct personas, while explicit capability refresh ensures users never view stale tenant controls after switching organizations or changing roles.

**Independent Test**: Can be tested by signing in as each of the five roles, retrieving the organization access context, verifying that the returned permission set matches the central role policy, confirming that UI navigation and action controls match each role's capabilities, switching organizations to verify immediate capability refresh and stale-state clearing, and confirming that directly invoking a hidden action still fails at the backend.

**Acceptance Scenarios**:

1. **Given** an active member of an active organization, **When** the client requests the current user's organization access context, **Then** the platform returns the verified organization identifier, membership identifier, current role, exact list of effective permissions for that role, and policy version—never exposing another member's permissions or internal credentials.
2. **Given** a `Viewer` signed into an organization, **When** they browse dashboards, sites, assets, monitoring, incidents, and work orders, **Then** they see read-only data with sufficient operational context and no enabled create, edit, assign, acknowledge, resolve, archive, or administration controls.
3. **Given** a multi-organization user who switches from Organization A (where they are `Owner`) to Organization B (where they are `Technician`), **When** the switch completes, **Then** previous-tenant view state is cleared, the organization access context is refreshed, administrative controls disappear, and if the user was on a page unavailable to their new role, they are routed safely or shown an accessible permission-denied state.
4. **Given** an authenticated user who navigates directly to an unauthorized route or whose permissions are revoked while a screen is open, **When** the backend rejects the request, **Then** the interface presents a clear, keyboard-accessible, non-color-only permission-denied or not-found state that never reveals whether a cross-tenant resource exists.

### User Story 5 - Enforce Authorization Across Real-Time Streams, Background Jobs, Exports, Devices, and Audit Trails (Priority: P2)

Authorization boundaries extend consistently beyond standard interactive requests to real-time event stream subscriptions, asynchronous background jobs, data exports, and telemetry device boundaries, with tamper-resistant security audit logging across all authorization-sensitive events. Real-time subscriptions validate organization membership and permissions per channel and revoke access when membership is lost; background jobs carry trustworthy actor provenance and re-validate tenant/resource ownership before mutating data; exports enforce tenant and role constraints from creation through short-lived download access; device telemetry identities remain strictly separate from human roles; and sensitive actions and denials are audited without leaking secrets.

**Why this priority**: Multi-tenant leaks frequently occur through secondary channels such as real-time streams, background workers, exported files, or conflated device/user credentials; unified enforcement and auditability ensure complete tenant isolation across the whole platform.

**Independent Test**: Can be tested by attempting cross-tenant real-time channel subscriptions and verifying disconnection upon membership suspension, enqueueing and executing background jobs with valid vs mismatched tenant/resource provenance, requesting and downloading telemetry/analytics exports across permitted and denied roles and tenants, verifying that human `Owner` credentials cannot publish device telemetry, and inspecting audit records for authorization denials, role changes, membership lifecycle changes, exports, and privileged simulator actions.

**Acceptance Scenarios**:

1. **Given** an authenticated user attempting to subscribe to a site's live telemetry, incident, or work-order event stream, **When** the subscription is requested, **Then** the platform resolves the target site's owning organization server-side, verifies the user's active membership and required read permission, rejects client-forged channel names, and terminates or revokes active subscriptions if the user's membership or organization is suspended or removed.
2. **Given** a background processing task triggered by a user action or system workflow, **When** the task is enqueued, **Then** the producer authorizes the initiating action first and attaches verified provenance (organization identifier, actor type `User`/`Device`/`System`, initiating user/membership where applicable, correlation identifier, and target resource identifier); **When** the worker executes the task, **Then** it re-validates tenant and resource ownership before mutating any data and never treats system tasks as an unrestricted cross-tenant superuser.
3. **Given** a `Facility Manager` or `Owner` requesting a telemetry or analytics export, **When** the export is generated and retrieved, **Then** only records belonging to the verified organization and authorized scope are included, download access is tenant-scoped and time-limited, and an `Engineer`, `Technician`, or `Viewer` attempting to trigger or download an export is denied.
4. **Given** an `Owner` user account and a provisioned telemetry device identity, **When** an attempt is made to use a human user's role to publish device telemetry or to use a device credential to access human administrative operations, **Then** both attempts are rejected because human RBAC and device telemetry publishing scopes are completely separate authorization domains.
5. **Given** any authorization-sensitive event—including an authorization denial, member role change, membership suspension/reactivation/removal, invitation grant/revocation, ownership transfer initiation/completion, sensitive export request/completion/failure, or privileged simulator control action—**When** it occurs, **Then** an immutable, tenant-scoped audit record is stored containing organization, actor, membership (when applicable), event type, target type/identifier, timestamp, correlation identifier, and safe metadata, with zero passwords, tokens, session credentials, invitation secrets, or raw sensitive payloads.

### Edge Cases

- **Multi-organization role isolation**: A user holding `Owner` in Organization A and `Technician` in Organization B switches tabs or submits interleaved requests to both organizations; each request MUST evaluate strictly against the target organization's membership without cross-request leakage.
- **Role downgrade or suspension during active work**: If an `Owner` downgrades a `Facility Manager` to `Viewer` or suspends their membership while that user has open views or active real-time subscriptions, the user's next protected action MUST be denied and active real-time subscriptions MUST be revoked according to session policy.
- **Concurrent last-owner removal/suspension/demotion**: When an organization has two active `Owner`s and two simultaneous requests try to suspend or remove both of them at the exact same moment, transactional concurrency control MUST allow at most one to succeed and reject the other so the organization never becomes ownerless.
- **Self-escalation and self-modification bounds**: A member MUST NOT be able to elevate their own role; an `Owner` attempting to change their own role via generic role update MUST be rejected (ownership handoff must use the dedicated ownership-transfer workflow).
- **Technician attempting privilege or scope escape**: A `Technician` attempting to list all organization work orders, inspect another technician's work order by guessing its identifier, change a work order's assignee or organization, or complete a work order no longer assigned to them MUST be denied without leaking foreign work-order existence.
- **Unknown role or undeclared permission policy**: Any route or operation missing an explicit permission requirement (unless explicitly marked public or user-scoped non-tenant) and any membership with an unrecognized role MUST fail closed and deny access.
- **Suspended or archived organization**: Even if a user's individual membership record is still marked `Active`, all organization-scoped operational requests MUST be denied when the owning organization is not `Active`.
- **Self-service notification preferences vs other users**: Although every role (`Owner`, `Facility Manager`, `Engineer`, `Technician`, `Viewer`) may read their own notifications and manage their own notification preferences, attempting to view or modify another member's notifications or preferences MUST be denied.
- **Engineer simulator control guardrails**: `Engineer` simulator control applies strictly to explicitly enabled non-production/demo simulation runs and MUST NEVER permit physical equipment control or actuation, nor operate outside demo-enabled environments.
- **Client-supplied authority spoofing**: Including `organizationId`, `membershipId`, `role`, or `permissions` in request bodies, query parameters, or client headers MUST NEVER override server-resolved membership and policy evaluation.
- **Cross-tenant parent-child mismatch**: Creating or updating a building, asset, sensor, threshold, incident, or work order that references a parent entity (site, building, asset, incident, or assignee) belonging to another organization MUST fail even if the caller holds `Owner` in the active organization.
- **Audit-log immutability and secret redaction**: Authorization denial logs MUST record enough safe metadata for security detection and support without exposing credentials, tokens, invitation secrets, or foreign-tenant record details to the caller or in audit storage.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST support exactly five fixed, organization-scoped member roles (`Owner`, `Facility Manager`, `Engineer`, `Technician`, `Viewer`) attached exclusively to a user's `Membership` in an `Organization` (never to the global `User` identity).
- **FR-002**: System MUST maintain a single, centralized, versioned, immutable permission catalogue using stable `<resource>:<action>` identifiers across five domains:
  - *Organization & Administration*: `organization:read`, `organization:update`, `organization:archive`, `members:read`, `members:invite`, `members:revoke-invitation`, `members:update-role`, `members:suspend`, `members:remove`, `audit-logs:read`.
  - *Infrastructure*: `sites:read/create/update/archive`, `buildings:read/create/update/archive`, `assets:read/create/update/archive`, `sensors:read/create/update/archive`, `thresholds:read/manage`, `devices:read/manage`.
  - *Monitoring & Intelligence*: `telemetry:read/export`, `monitoring:read`, `anomalies:read/acknowledge`, `predictions:read`, `risk-assessments:read`, `simulator:read/control`.
  - *Incidents & Maintenance*: `incidents:read/create/assign/investigate/resolve/close`, `incidents:add-related-note`, `work-orders:read`, `work-orders:read-assigned`, `work-orders:create`, `work-orders:assign`, `work-orders:update`, `work-orders:update-assigned`, `work-orders:complete`, `work-orders:complete-assigned`, `maintenance:read/manage`, `maintenance-records:create`.
  - *Analytics & Notifications*: `analytics:read/export`, `notifications:read`, `notifications:manage-preferences`.
- **FR-003**: System MUST maintain a single authoritative, immutable role-to-permission policy mapping covering all five roles, ensuring:
  - `Owner` receives all organization-scoped permissions in the catalogue (subject to dedicated ownership-transfer and last-owner protections); only `Owner` may update or archive organization settings, administer members/invitations/roles, or read organization audit logs.
  - `Facility Manager` receives full operational management across sites, buildings, assets, sensors, thresholds, devices read, telemetry/monitoring/analytics read and export, anomaly read/acknowledge, predictions/risk read, simulator read/control, full incident lifecycle (`read`, `create`, `assign`, `investigate`, `resolve`, `close`), full work-order lifecycle (`read`, `create`, `assign`, `update`, `complete`), maintenance schedule management, maintenance record creation, and self-service notifications—without organization administration, member/role management, or audit-log access.
  - `Engineer` receives read access to organization, sites, buildings, devices, monitoring, telemetry, anomalies, predictions, risk assessments, incidents, work orders, maintenance, and analytics; technical write access to create/update assets, create/update sensors, and manage thresholds (without site/building writes or archiving any infrastructure records); operational action permissions to acknowledge anomalies, create/investigate/resolve incidents (incident closure remains `Owner`/`Facility Manager`), create/update/complete work orders (work-order assignment remains `Owner`/`Facility Manager`), create maintenance records, control explicitly enabled demo simulator runs, and manage own notifications—without exports, member administration, or audit-log access.
  - `Technician` receives read access to organization, sites, and buildings; assignment-scoped operational read and execution permissions (`work-orders:read-assigned`, `work-orders:update-assigned`, `work-orders:complete-assigned`, `incidents:add-related-note`, `maintenance-records:create`, plus assignment-related reads on assets, sensors, telemetry, monitoring, anomalies, summary predictions/risk, incidents, and maintenance history); and self-service notifications—without analytics, exports, simulator control, or unassigned work-order access.
  - `Viewer` receives strictly read-only permissions across permitted operational views (organization, sites, buildings, assets, sensors, thresholds, telemetry, monitoring, anomalies, predictions, risk assessments, demo simulator status, incidents, work orders, maintenance, analytics) plus self-service notifications (`notifications:read`, `notifications:manage-preferences`) and zero write, create, update, assign, acknowledge, resolve, archive, or export permissions.
  - Every role receives self-service notification capabilities (`notifications:read` and `notifications:manage-preferences`) restricted strictly to the authenticated user's own notifications and preferences.
- **FR-004**: System MUST enforce a strict fail-closed, deny-by-default authorization pipeline on every organization-scoped operation in exact order: (1) authenticate user identity and verify active user status, (2) resolve target organization from trusted route/resource context (never from untrusted body claims), (3) verify active membership for `(user, organization)` and active organization status, (4) verify required permission(s) against the membership's current role, and (5) enforce service-level resource, parent-child tenant, assignment, and workflow-state policies.
- **FR-005**: System MUST treat missing permission declarations on any organization-scoped protected operation, missing organization context, or any unrecognized role value as an automatic authorization denial (never an implicit allow).
- **FR-006**: System MUST evaluate multi-permission declarations on an operation using strict conjunction (`ALL` listed permissions required); any future `ANY`-of-several semantics MUST require a separate explicit declaration rather than altering default conjunction behavior.
- **FR-007**: System MUST evaluate current membership status and role against authoritative server-side persistence on every protected organization-scoped request rather than relying on long-lived client-held role claims, so role downgrades, suspensions, and removals take effect on the very next request without requiring sign-out.
- **FR-008**: System MUST apply a consistent, strict non-disclosure error policy across all unauthorized and out-of-scope access attempts: unauthenticated callers receive an unauthenticated error; requests targeting an unjoined, non-existent, or inactive organization, an inactive or removed membership, or any cross-tenant child resource uniformly receive a concealed "Not Found" response without revealing existence or status; and only active members of an active organization lacking a required permission receive a "Forbidden" response.
- **FR-009**: System MUST enforce tenant scoping inside every data query and mutation for tenant-owned resources (including list queries, detail lookups, aggregations, updates, archives, and deletes), ensuring no tenant-owned record can be retrieved or mutated by global identifier alone.
- **FR-010**: System MUST validate same-tenant consistency across all parent-child and cross-entity relationships on write operations (including site-building, site/building-asset, asset/device-sensor, asset-incident, asset/incident-work order, and assignee-organization active membership), rejecting any cross-tenant reference.
- **FR-011**: System MUST enforce record-level and query-level assignment scoping for `Technician` work-order operations so that work-order list queries return only work orders assigned to the current technician, detail/update/completion operations verify both tenant ownership and assignee match, technicians cannot reassign work orders or change owning organization, and completion/maintenance-record submission re-verifies assignment and valid workflow state atomically at write time.
- **FR-012**: System MUST enforce strict assignment-related scoping for `Technician` access to non-work-order operational records so that a `Technician` may read `Assets`, `Sensors`, `Telemetry`, `Anomalies`, summary `Predictions/Risk`, `Maintenance History`, and `Incidents`—and add investigation notes on linked `Incidents` (`incidents:add-related-note`)—only when those records are linked to work orders assigned to that `Technician`, while retaining basic organization, site, and building read context for navigation and work location awareness.
- **FR-013**: System MUST enforce workflow-state and resource policies atomically at write time (preventing time-of-check/time-of-use race conditions) for incident investigation/resolution/closure, work-order assignment/update/completion, and membership administration.
- **FR-014**: System MUST restrict `Engineer` simulator control (`simulator:control`) through a resource and environment policy to explicitly enabled non-production/demo simulation runs only, and MUST NEVER allow any role—including `Owner`—to issue physical equipment actuation or control commands.
- **FR-015**: System MUST restrict organization membership administration (listing members, viewing member details, updating member roles, suspending/reactivating memberships, removing memberships, inviting members, and revoking invitations) exclusively to `Owner` members within the active organization, always scoping target membership lookups to both the target membership identifier and the verified active organization.
- **FR-016**: System MUST enforce role-management safety invariants on all membership and invitation mutations:
  - Prevent self-escalation of a user's own role.
  - Reject granting or revoking the `Owner` role through generic role-update or standard invitation flows (requiring a dedicated, explicitly confirmed, atomic ownership-transfer workflow for ownership changes).
  - Reject any demotion, suspension, or removal of an `Owner` that would leave an active organization with zero active `Owner`s, using transactional concurrency-safe validation so simultaneous requests cannot violate the last-active-owner invariant.
  - Return a clear conflict indication when an operation would violate the last-owner invariant or a stale state constraint.
- **FR-017**: System MUST provide an organization access-context capability for any active member of an active organization that returns their verified organization identifier, membership identifier, current role, effective permission list, and policy version for frontend presentation and diagnostics, while never treating client-held capability state as an authorization boundary.
- **FR-018**: System MUST integrate capability-driven role-aware visibility in the user interface—hiding or disabling unauthorized navigation items and actions (such as member administration for non-owners, asset creation for `Viewer`/`Technician`, and write controls for `Viewer`), refreshing capabilities and clearing previous-tenant UI state upon organization switch, role change, or session refresh, and rendering accessible (WCAG 2.2 AA, keyboard-navigable, non-color-only) permission-denied and read-only states.
- **FR-019**: System MUST enforce authentication, active organization membership, and resource-specific permission authorization on real-time event stream connections and every individual channel/room subscription (resolving target site/resource ownership server-side rather than trusting client-supplied room names) and revoke or disconnect active subscriptions upon sign-out, session revocation, membership suspension/removal, or organization suspension.
- **FR-020**: System MUST keep telemetry device authentication and topic publishing authorization completely separate from human organization RBAC: a human `Owner` role MUST NOT grant device publishing authority, and a device credential MUST NOT grant human application permissions.
- **FR-021**: System MUST enforce authorization at both job enqueue time and worker execution time for asynchronous background tasks: producers MUST verify caller authorization before enqueueing and attach trusted provenance (organization identifier, actor type `User`/`Device`/`System`, initiating user/membership when applicable, correlation identifier, and target resource identifier), while workers MUST re-validate tenant and resource ownership before mutating state and run system-initiated jobs under narrowly scoped service capabilities rather than unrestricted superuser privileges.
- **FR-022**: System MUST enforce tenant scoping and export permissions (`telemetry:export`, `analytics:export`) across export creation, asynchronous export generation, stored export artifacts, and short-lived, access-controlled download links so no export can include or disclose another organization's records.
- **FR-023**: System MUST record immutable, append-only, tenant-scoped security audit events for authorization denials (safe metadata only), membership role changes (including previous and new role), membership suspension/reactivation/removal, invitation grants and revocations, ownership transfer initiation and completion, sensitive export requests/completions/failures, and privileged simulator control actions—capturing organization, actor, actor membership (where applicable), event type, target type and identifier, occurrence timestamp, request/correlation identifier, and sanitized metadata while excluding passwords, tokens, cookies, invitation secrets, and unnecessary sensitive payloads.
- **FR-024**: System MUST document the required permissions and error behaviors for every protected organization-scoped operation in the platform's interface contracts and maintain explicit positive and negative automated verification across all five roles, cross-tenant boundaries, technician assignment rules, and concurrent last-owner protection.

### Key Entities *(include if feature involves data)*

- **Organization Role**: One of five fixed, predefined roles (`Owner`, `Facility Manager`, `Engineer`, `Technician`, `Viewer`) assigned to a `Membership` within a specific `Organization`, determining the baseline set of permitted actions for that user in that tenant.
- **Permission Identifier**: A stable, centrally versioned, action-oriented `<resource>:<action>` capability key (such as `organization:read`, `assets:create`, `work-orders:update-assigned`, `analytics:export`) mapped deterministically to one or more Organization Roles.
- **Organization Access Context**: A server-verified, per-request authorization context binding an authenticated `User`, an active `Organization`, an active `Membership`, the resolved `Organization Role`, the effective set of `Permission Identifier`s, and the current policy version.
- **Resource Access Policy**: A domain-level authorization rule evaluated on target records and queries that combines the `Organization Access Context` with record tenant ownership, parent-child tenant consistency, assignee ownership (for `Technician` work orders), workflow state, and environment eligibility (for demo simulator controls).
- **Authorization Audit Event**: An immutable, append-only, tenant-scoped security event record capturing organization identifier, actor user and membership identifiers, event type, target entity type and identifier, occurrence timestamp, request/correlation identifier, and redacted operational metadata.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of organization-scoped protected operations reject unauthenticated callers, inactive organizations, inactive/suspended memberships, unrecognized roles, and undeclared permission policies in automated security verification suites (zero fail-open paths).
- **SC-002**: 100% of cross-tenant access probes—including substituted resource identifiers, cross-tenant parent references, cross-tenant real-time channel subscriptions, cross-tenant exports, and tampered background-job payloads—are rejected with zero foreign-tenant records returned or modified and zero foreign resource existence leaked.
- **SC-003**: 100% of role-permission matrix combinations across all five roles (`Owner`, `Facility Manager`, `Engineer`, `Technician`, `Viewer`) pass both positive (permitted) and negative (denied) end-to-end verification tests, including 0% write/mutation permissions granted to `Viewer` and 0% unassigned work-order exposure or mutation allowed for `Technician`.
- **SC-004**: 100% of membership role downgrades, suspensions, and removals take effect on the affected user's immediate next protected request (0-request grace window requiring logout) and revoke active real-time subscriptions within the configured revocation window.
- **SC-005**: 100% of concurrent last-active-owner demotion, suspension, or removal stress tests preserve at least one active `Owner` per active organization and reject every generic role update or invitation attempting to assign or revoke `Owner`.
- **SC-006**: 100% of authorization-sensitive operations (role changes, membership lifecycle transitions, ownership transfers, authorization denials, sensitive exports, and privileged simulator controls) produce a queryable, immutable audit event linked to the originating correlation identifier, with 0% leakage of passwords, tokens, session credentials, invitation secrets, or raw sensitive payloads.
- **SC-007**: At least 95% of organization-scoped authorization evaluations and access-context lookups complete within the platform's interactive response budget (under 300 ms overall for ordinary authenticated read operations under standard MVP test workloads) without introducing cross-request authorization caching.
- **SC-008**: 100% of role-aware user interface views accurately reflect backend-provided capabilities for all five roles, refresh cleanly on organization switch without showing prior-tenant data, and pass keyboard-only navigation and non-color-only status checks (WCAG 2.2 Level AA) on permission-denied and read-only states.

## Assumptions

- **Prerequisites and Phased Sequencing**: Phase 5.3 builds directly on Phase 5.1 (Authentication & Identity Management, providing global `User`, authenticated identity context, and security audit records) and Phase 5.2 (Organizations & Multi-Tenancy, providing `Organization`, `Membership`, organization role assignments, organization/membership lifecycle statuses, and tenant scoping conventions). Because organization and membership records are not yet present in the current platform data model, Phase 5.2 foundations and baseline membership lifecycle must be established before or alongside Phase 5.3 implementation; Phase 5.3 does not introduce duplicate user, organization, or membership models.
- **Five-Role Canonical Model**: Per GridAware's Constitution (Principle I), PRD (§11), and the Phase 5.3 specification, the MVP uses exactly five fixed organization roles (`Owner`, `Facility Manager`, `Engineer`, `Technician`, `Viewer`), superseding older architecture draft references to a separate sixth `Admin` role.
- **Central Policy Definition & Live Evaluation**: For MVP, the role-to-permission matrix is maintained centrally as versioned, reviewable application policy rather than customer-editable permission tables, and active membership status/role is resolved live per request rather than cached across requests so downgrades and revocations apply immediately.
- **Dedicated Ownership Transfer Separation**: Ownership transfer uses a dedicated, explicitly confirmed, atomic workflow separate from generic member role updates; Phase 5.3 enforces the guardrails preventing generic role changes or invitations from assigning/revoking `Owner` and enforces concurrency-safe last-owner protection across all membership mutations.
- **Decision-Support Boundary (No Physical Control)**: Consistent with Constitution Principle II, no role—including `Owner`—receives permission to actuate or control physical equipment; simulator control applies strictly to synthetic simulation runs.
- **Explicitly Out of Scope**: User-defined/custom roles, visual permission builders, arbitrary per-user permission overrides, attribute-based policy administration UI, cross-organization resource sharing, external authorization servers/federation, billing/subscription entitlements, and per-site custom role grants are excluded from Phase 5.3.
- **Downstream Consumer Readiness**: Resource policies defined in Phase 5.3 (tenant scoping, incident/work-order policies, technician assignment scoping, simulator/export/real-time/background-job authorization contracts) establish the reusable authorization foundation consumed by upcoming domain capabilities (Sites, Buildings, Assets, Sensors, Telemetry, Intelligence, Incidents, Work Orders, Maintenance, and Analytics) as each domain is built.
