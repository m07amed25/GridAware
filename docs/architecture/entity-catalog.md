# GridAware — Entity Catalog and Attribute Specification

**Document ID:** ARC-DB-ENT-001  
**Version:** 0.1  
**Status:** Proposed for review  

---

## 1. Conventions

- IDs: UUIDs generated by the application/database; do not expose sequential database IDs.
- Timestamps: PostgreSQL `timestamptz`, represented by Prisma `DateTime`; persist UTC instants.
- Names: human-readable labels; codes: stable machine-readable identifiers.
- JSON: use only for variable/configuration/evidence payloads, not for core relational fields that need filtering or referential integrity.
- Tenant-owned rows: include `organizationId` unless there is a documented reason not to.
- Audit columns: `createdAt`, `updatedAt` where mutation is expected; append-only event/audit tables use `occurredAt`/`createdAt` and should not be silently updated.
- Soft removal: prefer lifecycle status or `archivedAt` for business records. Do not physically delete records that are referenced by operational history.

The tables below define logical attributes. Exact Prisma scalar types, relation field names, and nullability are finalized during schema implementation.

## 2. Identity and Organization

### User

**Purpose:** Global human identity; not tenant-owned.

| Attribute | Required | Notes |
|---|---:|---|
| id | Yes | UUID primary key |
| email | Yes | Globally unique normalized email |
| displayName | Yes | Name shown in UI |
| status | Yes | Active, invited/disabled policy as selected by auth design |
| emailVerifiedAt | No | Verification timestamp |
| createdAt / updatedAt | Yes | Audit timestamps |

Authentication provider identities, password hashes, sessions, and refresh tokens depend on the authentication decision in Phase 3.3. If local passwords are used, store only an appropriate password hash. Never store plaintext passwords or reusable tokens.

### Organization

**Purpose:** SaaS tenant and ownership root.

| Attribute | Required | Notes |
|---|---:|---|
| id | Yes | UUID |
| name | Yes | Display name |
| slug | Yes | Globally unique URL-safe identifier |
| status | Yes | ACTIVE, SUSPENDED, ARCHIVED |
| timezone | Yes | IANA timezone for display/scheduling defaults |
| createdAt / updatedAt | Yes | Audit timestamps |

### Membership

**Purpose:** Connects a User to an Organization and defines tenant-scoped role.

| Attribute | Required | Notes |
|---|---:|---|
| id | Yes | UUID |
| organizationId | Yes | Tenant owner |
| userId | Yes | Global user |
| role | Yes | OWNER, ADMIN, FACILITY_MANAGER, ENGINEER, TECHNICIAN, VIEWER |
| status | Yes | INVITED, ACTIVE, SUSPENDED, REMOVED |
| joinedAt | No | Set when activated |
| createdAt / updatedAt | Yes | Audit timestamps |

Constraint: unique `(organizationId, userId)`.

### Invitation (MVP if organization invites are in scope)

Fields: id, organizationId, normalized email, intended role, token hash, expiresAt, acceptedAt, revokedAt, invitedByUserId, createdAt. Store only a hash of the invitation token. Invitations must expire and be single-use.

## 3. Site and Building

### Site

Fields: id, organizationId, code, name, siteType (FACTORY / COMMERCIAL_BUILDING / OTHER), status, timezone, address fields or structured address, latitude/longitude if justified, createdAt, updatedAt, archivedAt.

Constraints: unique `(organizationId, code)`; site belongs to exactly one organization.

### Building

Fields: id, organizationId, siteId, code, name, buildingType, status, floor/area metadata where useful, createdAt, updatedAt, archivedAt.

Constraints: unique `(organizationId, siteId, code)`; building belongs to a site in the same organization.

## 4. Asset and Device Catalog

### AssetType

Global seeded catalog in the initial MVP. Fields: id, code, name, category, description, defaultMetricCodes, isActive. Avoid making customer-customizable asset types until there is a concrete need.

### Asset

Fields: id, organizationId, siteId, optional buildingId, assetTypeId, assetCode, name, description, manufacturer, model, serialNumber (optional/sensitive operational identifier), criticality, status, commissionedAt, decommissionedAt, specifications JSON, createdAt, updatedAt, archivedAt.

Constraints: unique `(organizationId, assetCode)`; building (if set) must be in the same site; asset type must be active for new registrations.

Criticality proposal: LOW, MEDIUM, HIGH, CRITICAL. Criticality is an operational ranking configured by authorized staff, not an AI prediction.

### Device

Fields: id, organizationId, siteId, deviceCode, name, kind (SIMULATOR / GATEWAY / DIRECT_SENSOR), status, credentialHash or credential reference, provisionedAt, lastSeenAt, revokedAt, metadata JSON, createdAt, updatedAt.

Constraints: unique `(organizationId, deviceCode)`. Credential rotation and revocation are mandatory before physical-device production integration.

### MetricDefinition

Global reference catalog. Fields: id, code, displayName, description, dimension, canonicalUnit, allowedUnits, displayPrecision, validationMin/Max (optional), isActive.

Example codes: `temperature`, `vibration`, `voltage`, `current`, `frequency`, `pressure`, `power`, `energy`, `operating_hours`.

### Sensor

Fields: id, organizationId, assetId, optional deviceId, metricDefinitionId, sensorCode, externalKey, name, status, canonicalUnit, samplingIntervalSeconds, staleAfterSeconds, installedAt, lastObservedAt, lastReceivedAt, metadata JSON, createdAt, updatedAt, archivedAt.

Constraints: unique `(organizationId, sensorCode)`; external key should be unique within its Device when present. A Sensor is tied to one Asset and one primary Metric Definition in the MVP.

### SensorThreshold

Fields: id, organizationId, sensorId, warningMin, warningMax, criticalMin, criticalMax, effectiveFrom, optional effectiveTo, enabled, configuredByUserId, version, createdAt.

Rules: validate min/max consistency; at least one bound must be present; warning bands must be less severe than critical bands; overlapping effective intervals for the same sensor should be prevented by service validation or database constraints. Preserve historical threshold versions.

## 5. Simulation

### SimulationRun

Fields: id, organizationId, siteId, assetId, deviceId, scenarioCode, status (CREATED / RUNNING / PAUSED / COMPLETED / STOPPED / FAILED), speedMultiplier, randomSeed, simulatorVersion, configuration JSON, startedAt, endedAt, createdByUserId, createdAt, updatedAt.

Rules:
- Simulation must target an asset and device owned by the same organization/site.
- Only authorized users may start/stop a run.
- Simulation output must be tagged as SIMULATOR at event ingestion.
- UI labels the run and derived telemetry as simulated/demo data.
- A run must not be able to publish to another tenant's topics.

Scenario codes initially include NORMAL_OPERATION, PROGRESSIVE_OVERHEATING, ABNORMAL_VIBRATION, COOLING_DEGRADATION, ELECTRICAL_INSTABILITY, and SUDDEN_SHUTDOWN. The catalog may live in code/config initially.

## 6. Telemetry

### TelemetryEvent

**Purpose:** One accepted source envelope/message.

| Attribute | Required | Notes |
|---|---:|---|
| id | Yes | Internal UUID |
| organizationId | Yes | Tenant scope |
| deviceId | Yes | Authenticated publisher |
| simulationRunId | No | Present for simulator source |
| source | Yes | SIMULATOR, DEVICE, IMPORT |
| sourceEventId | Yes | Stable publisher-provided ID |
| schemaVersion | Yes | Contract version |
| observedAt | Yes | Time measurement was observed |
| receivedAt | Yes | Time backend accepted message |
| quality/status | Yes | Event-level validation outcome |
| payloadHash | Yes | Optional integrity/dedup diagnostic |
| rawPayload | No | Optional short-lived diagnostic JSON |
| createdAt | Yes | Persistence timestamp |

Constraint: unique `(organizationId, deviceId, sourceEventId)`.

### TelemetryReading

**Purpose:** One normalized measurement inside an accepted TelemetryEvent.

Fields: id, organizationId, telemetryEventId, sensorId, assetId, metricCode, value (initially PostgreSQL double precision/Prisma Float), canonical unit, quality (VALID / SUSPECT / INVALID), observedAt, normalizationVersion, createdAt.

Constraints: unique `(telemetryEventId, sensorId)` if one event contains at most one reading per sensor. If the contract allows repeated samples from one sensor in one envelope, include a stable `sequence`/sample index in the uniqueness key.

Denormalized organizationId, assetId, and metricCode are intentional query/tenant-scoping fields; the ingestion transaction must derive them from the authenticated Sensor/Device mapping, not trust arbitrary client values.

## 7. Intelligence

### AnomalyEvent

Fields: id, organizationId, siteId, assetId, optional sensorId, optional telemetryEventId, detectionSource (RULE / MODEL), detectionCode, severity, score, status, deduplicationKey, windowStart, windowEnd, detectedAt, evidence JSON, optional modelVersionId, acknowledgedAt, resolvedAt, createdAt, updatedAt.

Constraint: define uniqueness for deduplication according to the event grouping policy. Do not globally unique a simple fingerprint if repeated incidents over time must be allowed. A time bucket or active-event rule may be required.

### ModelVersion

Fields: id, modelKey, taskType, version, artifactUri, framework, schemaVersion, status (REGISTERED / VALIDATED / STAGING / ACTIVE / RETIRED), evaluationMetrics JSON, trainedAt, registeredAt, metadata JSON.

Model artifacts live outside PostgreSQL; the row stores metadata and a controlled artifact reference.

### Prediction

Fields: id, organizationId, assetId, optional sensorId, modelVersionId, taskType, predictionHorizonSeconds, predictedValue (optional), failureProbability (optional), confidence (optional), predictionPayload JSON, explanationPayload JSON, predictedAt, validUntil, createdAt.

Rules: persist the model version; preserve prediction history; do not overwrite an earlier prediction; store validity/horizon and explainability payload version.

### RiskAssessment

Fields: id, organizationId, assetId, score, category, dataQualityScore, policyVersion, factorSnapshot JSON, assessedAt, validUntil, createdAt.

Risk score must be reproducible from stored factor/policy metadata where feasible. Missing or stale data must be represented explicitly and must not be silently treated as healthy.

## 8. Incidents and Maintenance

### Incident

Fields: id, organizationId, siteId, assetId, optional sourceAnomalyId, incidentNumber, title, description, severity, status, sourceType (ANOMALY / MANUAL / OTHER), assignedToUserId (optional), createdByUserId, detectedAt, acknowledgedAt, resolvedAt, closedAt, createdAt, updatedAt.

Constraints: unique `(organizationId, incidentNumber)`. A linked anomaly must belong to the same organization and asset. State changes require validation and history.

### IncidentEvent

Fields: id, organizationId, incidentId, actorUserId (nullable for system), eventType, fromStatus, toStatus, comment, metadata JSON, occurredAt.

Append-only. This table explains assignment, status change, acknowledgement, investigation note, escalation, and resolution events.

### WorkOrder

Fields: id, organizationId, siteId, assetId, optional incidentId, workOrderNumber, type (CORRECTIVE / PREVENTIVE / INSPECTION), status, priority, title, description, assignedToUserId, createdByUserId, dueAt, startedAt, completedAt, completionSummary, createdAt, updatedAt.

Constraints: unique `(organizationId, workOrderNumber)`. If linked to an Incident, both must share organization and asset unless a documented cross-asset work package is introduced later.

### MaintenanceSchedule

Fields: id, organizationId, assetId, name, recurrenceDefinition JSON or normalized interval fields, timezone, nextDueAt, enabled, createdByUserId, createdAt, updatedAt.

### MaintenanceRecord

Fields: id, organizationId, assetId, optional workOrderId, performedByUserId, maintenanceType, summary, findings JSON, performedAt, createdAt.

## 9. Platform and Integration Records

### Notification

Fields: id, organizationId, recipientUserId, category, title, body, targetType, targetId, readAt, createdAt, metadata JSON. In-app notification is the initial channel. Delivery provider records may be separate later.

### AuditLog

Fields: id, optional organizationId, optional actorUserId, action, entityType, entityId, requestId, occurredAt, metadata JSON, source IP/user-agent only where justified and privacy-reviewed.

Audit logs should be append-only to application roles. Avoid storing secrets or full sensitive payloads in metadata.

### OutboxEvent

Fields: id, organizationId, aggregateType, aggregateId, eventType, payload JSON, status, attempts, availableAt, publishedAt, lastErrorCode, createdAt.

Purpose: persist a durable event in the same database transaction as the business change, then publish it to BullMQ or another transport asynchronously. Workers must be idempotent because an outbox event can be published more than once.

## 10. Cross-Entity Constraints Checklist

- Asset.organizationId matches Site.organizationId.
- Asset.buildingId, when present, points to a Building with the same organizationId and siteId.
- Device.organizationId matches Device.siteId's organization.
- Sensor.organizationId and assetId point to the same tenant and Asset.
- Sensor.deviceId, when present, points to an authorized Device in the same tenant/site policy.
- TelemetryEvent.organizationId matches Device.organizationId.
- SimulationRun, TelemetryEvent, and Device ownership all match.
- TelemetryReading.organizationId, assetId, and sensorId are mutually consistent.
- AnomalyEvent, Prediction, RiskAssessment, Incident, and WorkOrder all match the target Asset's organization/site.
- Incident source anomaly belongs to the same Asset/tenant.
- WorkOrder incident link belongs to the same Asset/tenant under the MVP rule.
- Assigned users are active Members of the owning Organization and have suitable permissions.

These constraints must be implemented through composite foreign keys where practical, transactional validation, and tenant-scoped services. A normal single-column foreign key does not by itself prove same-tenant consistency.
