# GridAware — Prisma Schema Design Specification

**Document ID:** ARC-DB-PRI-001  
**Version:** 0.1  
**Status:** Design proposal; schema implementation is a later engineering task

---

## 1. Goals

The Prisma model must represent the logical database model while preserving PostgreSQL capabilities where needed. The design should provide type-safe access for NestJS and a controlled migration workflow against Neon PostgreSQL.

Prisma is the ORM and schema/migration tool. It is not the authorization system and does not replace tenant filtering, database constraints, or domain validation.

## 2. Version and Neon Integration Guardrails

The current official Prisma v7 PostgreSQL documentation supports Neon and describes putting connection configuration in the Prisma config file rather than the `datasource` block in `schema.prisma`. The current Neon guide recommends separate pooled runtime and direct CLI/migration URLs, and a Neon driver adapter for Prisma v7. See:

- [Prisma v7 PostgreSQL documentation](https://www.prisma.io/docs/orm/v7/core-concepts/supported-databases/postgresql)
- [Neon — Connect from Prisma](https://neon.com/docs/guides/prisma)
- [Prisma config reference](https://www.prisma.io/docs/orm/v7/reference/prisma-config-reference)

Version-sensitive rules:
- Pin `prisma`, `@prisma/client`, and `@prisma/adapter-neon` to compatible versions from the same supported major line.
- Do not blindly install `latest` without checking the stable release and Neon compatibility guide.
- Prisma ORM 7 uses the `prisma-client` generator with an explicit output path in the current setup guides.
- In Prisma ORM 7, configure the datasource URL in the appropriate Prisma config file; do not copy Prisma 6 `url = env(...)` examples into a v7 schema.
- Prisma 7.10+ may generate `prisma7.config.ts`; edit the config file generated by the installed version and do not create competing config files.
- Use the pooled Neon URL for application queries and direct/unpooled URL for Prisma CLI/migrations according to the current adapter guide.

## 4. Generator and Data Source Pattern

Illustrative Prisma v7 schema header:

```prisma
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}
```

Illustrative Prisma CLI config pattern (adapt the filename and environment variable names to the selected Prisma 7 minor version and generated project):

```ts
import "dotenv/config";
import { defineConfig, env } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: {
    path: "prisma/migrations",
  },
  datasource: {
    url: env("DATABASE_URL_UNPOOLED"),
  },
});
```

Runtime environment variables:

```env
# Pooled URL for application traffic via Neon adapter
DATABASE_URL="postgresql://...-pooler..."

# Direct / unpooled URL for Prisma CLI migration operations
DATABASE_URL_UNPOOLED="postgresql://..."
```

Do not commit credentials. Use separate Neon branches/credentials for development, staging, and production.

## 5. Runtime Client Pattern

The selected Neon adapter pattern should be implemented in one NestJS provider and injected through a global or shared Database module. Do not instantiate PrismaClient in every service.

Conceptual example (generated import path depends on schema output):

```ts
import { Injectable, OnModuleDestroy, OnModuleInit } from "@nestjs/common";
import { PrismaNeon } from "@prisma/adapter-neon";
import { PrismaClient } from "../generated/prisma/client";

@Injectable()
export class PrismaService extends PrismaClient
  implements OnModuleInit, OnModuleDestroy {
  constructor() {
    const connectionString = process.env.DATABASE_URL;
    if (!connectionString) {
      throw new Error("DATABASE_URL is required");
    }

    const adapter = new PrismaNeon({ connectionString });
    super({ adapter });
  }

  async onModuleInit() {
    await this.$connect();
  }

  async onModuleDestroy() {
    await this.$disconnect();
  }
}
```

Confirm the exact adapter constructor/API against the installed `@prisma/adapter-neon` version during Phase 4. Avoid copying this conceptual snippet without compiling it against the pinned dependencies.

## 6. Modeling Conventions

- Use UUID primary keys for externally referenced entities.
- Use explicit enums for stable finite state sets.
- Use `@map`/`@@map` only when a database naming convention requires it; choose one convention and apply consistently.
- Prefer singular model names in PascalCase and SQL table mapping consistently (e.g. `Organization`, `TelemetryReading`).
- Use `createdAt @default(now())` and `updatedAt @updatedAt` for mutable records where appropriate.
- Avoid `@updatedAt` on append-only event/history tables.
- Use `Decimal` for financial quantities or exact decimal requirements; use `Float`/PostgreSQL double precision for initial engineering telemetry where the instrument precision and domain tolerate floating-point representation. Document rounding at display boundaries.
- Use `Json` for flexible evidence/configuration snapshots only; do not put core filterable relationships into JSON.
- Store timestamps as timezone-aware PostgreSQL instants and normalize API serialization to ISO 8601 UTC.
- Add explicit indexes for actual query patterns.

## 8. Relations and Tenant Consistency

A relation in Prisma does not automatically guarantee that all related rows belong to the same tenant if the relation only references a globally unique `id`.

For critical tenant-owned relationships:
- Prefer composite unique keys containing `organizationId` where needed.
- Use composite foreign keys so the same `organizationId` participates in the relation, where Prisma can represent it safely.
- Where the schema requires a database constraint not expressible in Prisma's model syntax, add a reviewed SQL migration and document it.
- Add service-level ownership checks even when composite foreign keys exist.

Do not rely on a convention like “the frontend always sends the correct organizationId.”

## 9. Telemetry Mapping

Recommended Prisma models:
- `TelemetryEvent`: event envelope and idempotency identity.
- `TelemetryReading`: one normalized value per Sensor/event sample.

The event uniqueness constraint should cover `(organizationId, deviceId, sourceEventId)`. The reading uniqueness constraint should match the selected message contract, initially `(telemetryEventId, sensorId)` if one reading per Sensor per envelope is guaranteed.

The high-volume `TelemetryReading` model should have only the indexes justified by measured chart and investigation queries. Keep raw JSON optional and apply separate retention.

## 10. Database-Level Features Beyond Prisma

Some PostgreSQL features may require SQL migrations or manual verification:
- Composite tenant foreign keys.
- Partial indexes (e.g. pending outbox, unresolved incident queues).
- Check constraints for mutually exclusive or ordered numeric bounds.
- Exclusion constraints for overlapping threshold effective intervals, if adopted.
- Triggers only when no safer application/constraint approach exists.
- Native partitioning if later benchmarked and approved.
- RLS policies if chosen after pooled-connection context is proven.

Prisma schema introspection may not fully preserve every custom database feature. Document them in migration comments and add schema drift checks.

## 11. Migration Workflow

Development:
1. Update `schema.prisma`.
2. Review model and relation diffs.
3. Run formatter and generate.
4. Create a named migration.
5. Review generated SQL manually.
6. Add any required custom SQL constraints/indexes.
7. Apply to a disposable/development Neon branch.
8. Run migration and integration tests.
9. Commit schema and migration together.

Production:
- Use `prisma migrate deploy` with the direct/unpooled migration connection configured for the selected version.
- Never use `migrate dev` against production.
- Do not use `db push` as the production migration strategy.
- Use expand-and-contract for breaking changes.
- Back up/verify recovery according to the release plan.

## 12. Seed Data

Seed only stable reference data and development fixtures:
- AssetType catalog.
- MetricDefinition catalog.
- Simulator scenario catalog if stored.
- Development-only organization/site/generator/sensor fixture.

Never insert demo fixtures into production implicitly. Seed scripts must be idempotent and must not create a default shared admin password.

## 13. Prisma Design Review Checklist

- [ ] Generator and output path match the installed Prisma version.
- [ ] Neon adapter and packages are version-aligned.
- [ ] Runtime uses pooled URL as documented for the adapter.
- [ ] CLI/migrations use direct URL.
- [ ] No credential is committed.
- [ ] Every tenant-owned model has a tenant scope strategy.
- [ ] Critical relations preserve same-tenant ownership.
- [ ] Telemetry idempotency constraints are explicit.
- [ ] Indexes map to documented query patterns.
- [ ] Event/history tables are append-only where required.
- [ ] Custom SQL migrations are documented and tested.
- [ ] Schema and migration history are committed together.

## 14. Implementation Boundary

This document defines how the Prisma schema should be designed. The actual production `schema.prisma`, generated client, NestJS Prisma provider, and migrations belong to Phase 4 after this design is reviewed and Phase 3.3 contracts are complete.
