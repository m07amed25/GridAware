# GridAware — Content Design and Terminology

**Document version:** 1.0  
**Status:** Proposed product language standard  
**Primary interface language:** English (initial baseline)  
**Future localization:** Arabic and other organization-selected languages  
**Related documents:** `screen-inventory.md`, `interaction-specifications.md`, `alert-notification-ux.md`, `accessibility-specification.md`

---

## 1. Purpose

This document standardizes the language used across GridAware so the same operational concept is not named differently on different pages. Clear language is especially important when users make decisions based on alerts, equipment states, telemetry quality, and maintenance tasks.

The initial UI language is English to align with the current product and engineering baseline. The content model should be localization-ready: avoid concatenating sentence fragments, keep dates/numbers/units locale-aware, and do not bake translated text into backend status codes.

## 2. Voice and tone

GridAware should sound:

- Professional and calm.
- Precise, not alarmist.
- Operationally helpful.
- Direct and concise.
- Transparent about uncertainty and missing data.

Avoid:

- Marketing exaggeration inside operational workflows.
- Claims that an AI prediction is certain.
- Vague warnings such as `Something went wrong` when the cause/action is known.
- Blame-oriented language.
- Unexplained abbreviations.
- Overuse of exclamation marks.

## 4. Status vocabulary

### Asset operational status

- `Operational`
- `Attention Required`
- `Degraded` (only when the product defines a supported state)
- `Out of Service`
- `Unknown`

### Device connection status

- `Online`
- `Offline`
- `Reconnecting`
- `Unknown`

### Telemetry freshness/quality

- `Live`
- `Delayed`
- `Stale`
- `Partial Data`
- `Invalid Data`
- `Unavailable`
- `Simulated`

### Alert lifecycle

- `Open`
- `Acknowledged`
- `Resolved`
- `Suppressed`

### Incident lifecycle

Use the workflow state names defined in the PRD and incident specification. Do not reuse `Acknowledged` as an incident state unless the domain model explicitly supports it.

### Work order lifecycle

Use distinct labels such as `Draft`, `Open`, `Assigned`, `In Progress`, `Blocked`, `Completed`, and `Cancelled` only where the backend workflow supports those states.

## 5. Naming conventions

- Page names use clear nouns: `Assets`, `Incidents`, `Work Orders`, `Analytics`.
- Actions use verbs: `Create asset`, `Assign technician`, `Acknowledge alert`, `Resolve incident`.
- Avoid vague buttons: `Submit`, `Proceed`, `OK` when a more descriptive action is possible.
- Use sentence case for headings and button labels.
- Use consistent capitalization for proper product terms: GridAware, EVARAX, MQTT, AI, API.
- Use singular entity labels in forms and plural labels in collections.

## 6. Microcopy patterns

### Empty states

Structure:

1. What is empty?
2. Why might it be empty?
3. What can the user do next?

Examples:

- **No assets yet** — Add an asset to begin monitoring this site.
- **No incidents found** — Try changing the filters or date range.
- **No telemetry available** — This asset has not received usable measurements for the selected period.
- **No notifications** — You're up to date.

### Loading states

Prefer meaningful status:

- `Loading asset details…`
- `Retrieving telemetry…`
- `Connecting to the simulator…`

Avoid a generic full-screen spinner when a local skeleton or inline loading state is sufficient.

### Error states

Structure:

- What failed.
- What was saved or not saved.
- What the user can do.

Examples:

- `We couldn't save the sensor configuration. Your previous settings are unchanged. Try again.`
- `Telemetry is temporarily unavailable. The last received measurement was at 10:42 UTC.`
- `You don't have permission to assign this work order. Contact an organization administrator.`

### Confirmation messages

- `Asset created.`
- `Technician assigned to work order WO-1042.`
- `Incident marked as resolved.`

Avoid vague success: `Done!`

## 7. AI language rules

- Say `The model detected an anomaly` rather than `The system knows the equipment is failing`.
- Say `Elevated risk estimate` rather than `Failure is certain`.
- State the prediction horizon whenever showing a time-bound prediction.
- Label uncalibrated outputs as `Model score`, not `Probability`.
- Explain that contributing features are model explanations, not confirmed physical root causes.
- Make data sufficiency visible: `Insufficient data for a reliable assessment`.
- Distinguish model unavailability from low risk.

## 8. Simulator language rules

- Display a persistent `SIMULATED` or `DEMO DATA` label in simulation contexts.
- Use `Start simulation`, `Pause simulation`, `Resume simulation`, and `Stop simulation`.
- Do not use `Start equipment` or `Power on generator`, which could imply control of physical equipment.
- Use `Inject simulated fault` for scenario controls.
- Make it explicit when generated alerts/incidents are demonstration records.

## 9. Numeric, date, and unit formatting

- Use a consistent locale-aware number/date formatter.
- Show units alongside values; avoid unitless telemetry.
- Preserve precision appropriate to the sensor and metric; do not display meaningless decimals.
- Use a consistent timezone convention and identify the timezone in relevant contexts.
- Use an em dash for unavailable values only when paired with an explanation/tooltip or explicit label; do not imply zero.
- Never replace missing values with zero.
- Percentages must include their denominator/definition when used for operational KPIs.

## 10. Localization readiness

- Store machine-readable enum values separately from localized display labels.
- Avoid building sentences from multiple translated fragments.
- Allow labels to expand by at least 30–40% in layouts where practical.
- Support right-to-left layout if Arabic localization is added.
- Mirror directional icons only when their meaning is directional; do not mirror logos or non-directional symbols.
- Ensure dates, numbers, and units use locale-aware formatting.

## 11. Content review checklist

- [ ] The same domain entity uses the same term throughout the product.
- [ ] Severity and lifecycle labels are not mixed.
- [ ] AI outputs communicate uncertainty and horizon.
- [ ] Simulated data is unmistakably labeled.
- [ ] Empty/error/success messages explain the next step.
- [ ] Numeric values include units and useful precision.
- [ ] No missing value is represented as zero or healthy.
- [ ] Text can be localized without layout breakage.
